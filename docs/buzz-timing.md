# 早押しの時刻同期と遅延補正の検証

## 背景と目的

LAN 内の Wi-Fi 環境では、参加者の端末（スマートフォン・PC）とサーバー間の通信に遅延とジッターが発生します。
早押しの判定において、単にサーバーへのパケット到達時刻だけで順番を決めると、通信遅延が大きい端末（Wi-Fi の電波が弱い、モバイルブラウザのバックグラウンド処理遅延など）が不利になります。

本システムでは以下の仕組みにより公平な早押し順序の決定を実現しています。

1. **時刻同期 (NTP 方式)** (`src/client/lib/clock.ts`):
   - 接続時に 5 回、その後 15 秒ごとに `time` イベントで ping を送受信。
   - 直近 12 件のうち、往復時間 (RTT) が最小のサンプルからクライアントとサーバーの時計オフセットを推定。
2. **高精度な押下時刻の取得** (`src/client/components/BuzzButton.tsx`):
   - タッチ操作: `touchstart` (`passive: false`)
   - マウス操作: `pointerdown`
   - キーボード操作: `keydown` (Enter / Space)
   - `performance.timeOrigin + event.timeStamp` からエポック時刻を算出し、推定オフセットを加えてサーバー時刻に換算。
3. **サーバー側での遅延補正** (`src/shared/buzz.ts`):
   - 申告された押下時刻を `[受信時刻 - BUZZ_GRACE_MS, 受信時刻]` の範囲に丸め、さらに出題開始時刻より前にならないように制限。
   - `BUZZ_GRACE_MS` の既定値は `500` (ミリ秒)。
   - 未判定の押下を、補正後の押下時刻順（同着の場合は受信時刻順）に並べ替えて回答権を割り当て。

本ドキュメントは、実機環境（iOS Safari、Android Chrome、PC Chrome など）でこの仕組みを検証し、その結果とパラメータ妥当性を記録するためのものです。

## 診断と分析の仕組み

### 1. 参加者画面のリアルタイム診断表示
- 参加者画面 (`/games/:id/play`) の上部ヘッダーを 0.5 秒長押しするか、ヘッダー内の「診断」ボタンをタップすると、診断パネルが表示されます。
- 表示内容:
  - **接続状態**: 接続中 / 切断中
  - **接続方式**: `websocket` / `polling`
  - **推定時計差 (offset)**: サーバー時刻との推定差分 (ms)
  - **最小往復時間 (RTT)**: 最小サンプルの往復遅延 (ms)
  - **推定サーバー時刻**: 同期されたミリ秒単位の現在時刻

### 2. イベントログへの診断情報の記録
- ボタン押下時に送信される `buzz` コマンドには、その瞬間の `diag: {rtt, offset}` がメタデータとして付与されます。
- SQLite の `events` テーブルにイベントログとしてそのまま保存されます。

### 3. 早押し分析スクリプト (`scripts/buzz-report.ts`)
- コマンド:
  ```sh
  node scripts/buzz-report.ts <gameId>
  ```
- 引数なしで実行すると直近のゲーム一覧が表示されます。
- 出力内容:
  - 各問題の各押下について: 補正後順位、受信順位、並べ替え有無、申告時刻、受信時刻、補正量、RTT、Offset
  - サマリー統計: 並べ替え発生回数・割合、RTT 分布 (最小・中央値・平均・95%tile・最大)、参加者別統計

## BUZZ_GRACE_MS (500ms) の設計と妥当性考察

### なぜ 500ms なのか
- 一般的なローカル Wi-Fi 環境における RTT は 5〜50ms 程度、ジッターや瞬間的な混雑があっても 100〜300ms 程度に収まります。
- 補正猶予を 500ms とすることで、電波状況による一時的なパケット遅延で 200〜400ms 遅れて届いた正当な押下を救済できます。

### 広すぎることのリスク (チート・不正申告)
- クライアント側で改ざんされたスクリプトを動かし、意図的に過去の時刻 (`受信時刻 - 500ms`) を申告した場合、最大 500ms 分「早く押した」と主張できてしまいます。
- ただし、出題開始時刻より前には遡れない (`Math.max(startedAt, ...)`) ため、出題直後であれば不正の余地は出題開始からの経過時間内に限定されます。
- 一般に人間の反応速度の限界は約 150〜200ms であるため、出題から 200ms 以内に押された場合は物理的限界に近い値となります。

### 狭すぎることのリスク (遅延端末の切り捨て)
- もし猶予を 100ms など短くしすぎると、Wi-Fi の一瞬の再送遅延 (RTT 150ms など) が発生した際に「正当に早く押していた参加者」の申告時刻が受信時刻 - 100ms に切り捨てられ、後から押した近距離・低遅延の参加者に負けてしまいます。

### 結論と基準
- LAN 内 Wi-Fi での運用を前提とすると、通常の RTT 分布が 100ms 未満であれば 500ms は十分かつ安全な値です。
- 実機検証において RTT の 95%tile が 100ms 未満であり、不当な逆転や違和感がなければ **既定値 500ms を維持** します。
- もし Wi-Fi の状態が極めて安定しており (RTT < 30ms)、より不正防止を厳格にしたい場合は 300ms 程度への引き下げも検討可能です。

## 既知の制約と対応

### 1. Wake Lock API (画面スリープ防止)
- **制約**: LAN 内の HTTP (`http://192.168.x.x:...`) はブラウザの仕様上「安全なコンテキスト (Secure Context)」ではないため、Screen Wake Lock API が無効化されます。
- **対応**: 
  - 参加者への事前アナウンス: スマートフォンの設定で「自動ロック」「画面消灯」を一時的に「なし」または長めの時間に設定してもらう。
  - スリープ復帰対策: 端末がスリープして画面が消えた場合でも、復帰時に Socket.IO が自動再接続・自動再購読を行い、最新の状態に即時復旧する設計となっています。

### 2. iOS Safari でのダブルタップ拡大
- **制約**: 連続タップ時にブラウザがダブルタップ拡大（ズーム）を行ってしまうと、早押し操作が阻害される。
- **対応**:
  - `BuzzButton.tsx` の `touchstart` リスナーで `event.preventDefault()` を呼出 (`passive: false`)。
  - `BuzzButton.module.css` に `touch-action: manipulation;` および `-webkit-touch-callout: none;`、`user-select: none;` を設定。
  - 実機検証でボタンを素早く連打しても拡大されないことを確認。

## 実機テスト手順と検証項目

### 推奨環境
- **Wi-Fi**: 会場と同等（または本番で使用する）Wi-Fi ルーター
- **検証端末**:
  1. iOS 端末 (iPhone / Safari)
  2. Android 端末 (Android / Chrome)
  3. PC (Chrome)

### 手順
1. **サーバー起動**:
   ```sh
   npm run dev
   # または本番モード: npm run build && npm start
   ```
2. **ゲーム作成と接続**:
   - PC で `/admin` を開き、テスト用のシンプル早押しクイズを作成。
   - モニター画面 (`/games/:id/monitor`) を PC または別ディスプレイで開く。
   - 司会者画面 (`/games/:id/host`) を PC で開く。
   - 各検証端末（iOS, Android, PC）で参加者画面 (`/games/:id/play`) を開き、参加者名を登録。
3. **診断情報の確認**:
   - 各端末のヘッダーを長押し、または「診断」ボタンをタップ。
   - `websocket` で接続されていること、オフセットが妥当な値 (数 ms 〜 数十 ms)、RTT が 50ms 未満程度であることを確認。
4. **同時押下テスト**:
   - 司会者が「次の問題を出題」を押す。
   - モニター画面の合図（問題表示など）または口頭の合図で、複数の端末で同時に早押しボタンを押す。
   - 20〜30 回程度くり返し実施。
   - 端末の持ち手を交代し、人の反応差と端末の差を分離して観察。
5. **特殊環境テスト**:
   - **スリープ復帰**: スマートフォンを一度ロック（画面消灯）し、数秒後にロック解除して復帰した際、即座にボタンが押せる状態に同期されるか。
   - **連打・ダブルタップ**: iOS Safari でボタンを素早く連打しても画面がズームしないか。
6. **レポート出力**:
   ```sh
   node scripts/buzz-report.ts <gameId>
   ```
   - 並べ替え発生回数、RTT 分布、各端末の補正状況を確認。
