# 全体設計・拡張計画

## 目的

オフラインイベントで行う複数のクイズ企画で共通して使う、LAN 内限定の Web アプリ。
司会者・参加者・モニター・問題編集の4画面がリアルタイムに同期する。
企画 (mode) はプラグインとして追加できるようにする。

| 企画 | mode ID | 司会者 | 参加者 | モニター | 編集 | 感想戦 |
|---|---|---|---|---|---|---|
| シンプル早押しクイズ | `simple-buzzer` | ○ | ○ | ○ | ○ | ○ |
| 早押しクイズ (ボード付き) | `buzzer-board` | ○ | ○ | ○ | ○ | ○ |
| リスニング数学 | `listening-math` | – | – | ○ (再生と操作) | ○ | ○ (モニターから操作) |
| イラスト回文クイズ | `palindrome` | ○ | ○ | ○ | ○ | – |

## 技術スタック

| 用途 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript 7 (ネイティブ版 `tsc`) | 型チェック専用 (`noEmit`)。トランスパイルは Vite と Node の型ストリップが行う |
| フロントエンド | React 19 + Vite 8 + CSS Modules + React Router | |
| テスト | Vitest | 純粋な reducer の単体テストと、サーバーの結合テスト |
| リアルタイム通信 | Socket.IO 4 | 自動再接続、room、ack が使える。スマホのスリープ復帰に強い |
| HTTP | Hono + `@hono/node-server` | 静的ファイル配信、将来のメディアアップロード API |
| 永続化 | `node:sqlite` (Node 組み込み) | 依存なしでイベントログとスナップショットを保存する |
| バリデーション | zod 4 | コマンド payload と問題データ |
| Lint / Format | Biome | typescript-eslint は TS7 の JS API に依存するので使わない |
| サーバー実行 | Node 24 のネイティブ型ストリップ | ビルド不要。`erasableSyntaxOnly` を有効にする (enum などは使わない) |

## 中核の設計

### Game と Mode

- **Game** は1つの企画の実施インスタンス (`id, mode, title, questions, participants, state`)。
  リハーサル用と本番用のように、同じ mode で複数の Game を作れる。
- **ModeDefinition** (`src/shared/modes/types.ts`) は次のものを持つ:
  - `questionExtraSchema`: 企画ごとの問題の追加フィールド (genre、画像、ヒント、音声など)
  - `commandSchema`: 企画固有のコマンド (zod の discriminated union)
  - `permissions`: コマンドごとに実行できる role
  - `initialState()` / `apply(game, command, ctx)`: エンジンが渡した Game のコピーを書き換える。`ctx` にサーバー時刻と実行者が入る。
    外部の状態に依存しないので、イベントログを再生すれば同じ状態を再現できる (取り消しに使う)
  - `project(game, viewer)`: 閲覧者ごとに送る情報を絞る (参加者やモニターに未出題の答えを送らない)
- クライアント側の `src/client/modes/registry.ts` に、mode ごとの画面コンポーネントを登録する。

**新しい企画を追加する手順**: `src/shared/modes/<mode>/` に ModeDefinition を書く → shared の registry に登録 →
`src/client/modes/<mode>/` に画面を書く → client の registry に登録。サーバー側のコードは変えなくてよい。

### 同期モデル (サーバーが唯一の正)

1. クライアントは `command` を送るだけ。
2. サーバーは権限を確認し、zod で検証してから `apply` を適用する。
3. イベントを SQLite に追記し、Game のスナップショットを更新する。
4. 閲覧者の種類ごとに `project()` した Game 全体をブロードキャストする (単調増加の `version` 付き)。

- room は `game:{id}:host` / `:monitor` / `:participant:{pid}`。
- 数十人規模なので差分は送らず、毎回 state 全体を送る。
- 問題の編集も共通コマンド (`questions.*`) として同じ経路を通るので、編集画面と司会者画面が常に一致する。
- 取り消し (undo): 直近の操作 (問題の編集と参加登録を除く) を除いてイベントログを最初から再生し、状態を作り直す。
- イベントログは感想戦や監査にも使える。

### 認証 (LAN 前提の軽いもの)

- 参加者: 名前を登録するとサーバーがトークンを発行する。トークンは localStorage に保存し、再読込しても同じ参加者に戻れる。
- 司会者と問題編集: 環境変数 `HOST_PASSWORD` で保護する (未設定なら誰でも使える)。
- モニター: 閲覧のみなので認証しない。ただし答えなど秘匿すべき情報は投影で除く。

### 早押しの公平性

- クライアントはサーバーと ping を交換して時計のオフセットを推定する (NTP 方式で、RTT が最小のサンプルを採用)。
- `touchstart` / `pointerdown` / `keydown` (Enter・Space) で押した瞬間の時刻をサーバー時刻に換算して送る。
- サーバーは申告された時刻を `[受信時刻 - 500ms, 受信時刻]` に丸めて使う。まだ判定していない押下だけを時刻順に並べ直す。

### モニター (16:9)

`MonitorStage` が 1920×1080 固定のステージを `transform: scale()` で画面に合わせる。スクロールは出さない。

### URL

| URL | 画面 |
|---|---|
| `/` | ゲーム一覧 |
| `/admin` | ゲーム作成と管理 |
| `/games/:id/host` | 司会者 |
| `/games/:id/play` | 参加者 (未登録なら名前を登録) |
| `/games/:id/monitor` | モニター |
| `/games/:id/edit` | 問題編集 |

## 企画ごとの拡張計画

### simple-buzzer (フェーズ1)

- 押した順に回答権を得る。正解 +1、誤答 -1。誤答した人はその問題でボタンを押せない。
- 押した人が全員誤答したら読み上げを再開する。参加者全員が誤答したら問題を終了する。
- 司会者の補正操作: 押下のリセット、問題のスキップ、再オープン、得点の直接編集、参加者の削除。
- 出題ごとの記録 `history` (出題前の得点、押下と判定) を残しておき、感想戦で使う。

### buzzer-board

- simple-buzzer の reducer とは別に実装する。ただし押下の受付や時刻補正などの部品は共通化する。
- 追加する state: 休みの残り問題数、勝ち抜け、連答カウンタ、ジャンル選択権、ボード回答 (提出、仮判定、確定)。
- 問題の追加フィールド: `genre` (13種)。次の問題はジャンルの中からランダムに選ぶ (乱数シードをコマンドに埋め込んで決定論的に選択する)。

#### 仕様と解釈の決定事項
- **その時点での早押し参加者の数**: 誤答した時点で勝ち抜けていない参加者の数 (誤答した本人を含み、休み中の人も含む)。誤答時の休み問題数は `min(その時点での早押し参加者の数, 5)` 問。
- **休みの消化**: 休み中の人は、以後に出題された問題の数だけ休み数が減る (スルーでボードクイズになった問題も1問と数える)。出題が取り消された (cancel) 問題は数えない。
- **連答が途切れる条件**: 直前の問題でその人が早押しで正解していなければ途切れる (他の人の正解、誤答、スルー、出題の取り消し)。
- **勝ち抜けた人の点**: 5ポイントに達したら早押しパートを勝ち抜け。早押しパートで獲得できるポイントの上限は5点であり、5点を超えたら5に戻す。5ポイントに戻したあと、ボードクイズの正解で5を超えて得点できる。
- **ジャンルの自動選択**: 1問目、誤答の次の問題、スルー (ボードクイズ) の次の問題では、「未出題の問題が最も多いジャンル」が自動で選ばれる。同数のジャンルが複数あるときはジャンル一覧の定義順 (ノンジャンル、スポーツ、世界史、公民、地理、文学、日本史、漫画・アニメ・ゲーム、生活、科学、芸能、芸術、言葉) で先頭のものが選ばれる。
- **ジャンル選択権**: 早押しで正解した人が次のジャンルを選べる。正解者が勝ち抜けた場合 (5ポイントに達した場合) もジャンルを選択できる。
- **回答権**: 最初に押した1人のみ。2番目以降の押下は記録するが回答権は与えられず、判定が出た時点でその問題は終了する。

### listening-math

- 問題の追加フィールド: `audio` (アップロードしたファイルの ID)。
- モニター画面が再生を担当する。state は `mode: 'playing' | 'review'` と現在の問題番号を持つ。

### palindrome

回文を表すイラストと文字数を見て、ひらがなの回文を答える。司会者が問題を終了するまで、参加者は何度でも回答できる。
参加者はヒントを自分の判断で開けられるが、開けるとペナルティの時間が正解時間に加わる。AI も参加者として参加する。

#### 問題のデータ

| フィールド | 例 | 説明 |
|---|---|---|
| `answer` (共通) | `まくらからくま` | 想定解。ひらがなの回文。保存時に検証する |
| `extra.image` | メディア ID | 回文を表すイラスト (#12 でアップロード) |
| `extra.notation` | `枕から熊` | 自然な表記。文字種ヒントの元になり、終了後にモニターにも出す |
| `extra.altAnswers` | `[]` | 別解 (ひらがなの回文)。省略可 |
| `extra.hints.situation` | 動物がある寝具から出てきているようです。 | 状況説明ヒント |
| `extra.hints.irasutoya` | 「枕のイラスト」、「熊のキャラクター（四つ足）」が使われています。 | いらすとやヒント |
| `extra.hints.charTypes` | `漢ああ漢` | 文字種ヒント。省略すると `notation` から自動で作る |

- 文字種ヒントの自動生成: `notation` の各文字を、ひらがな → `あ`、カタカナ → `ア`、漢字 → `漢`、英字 → `A` に置き換える。
  長音「ー」は直前の文字と同じ文字種にする。自動生成がおかしいときだけ `charTypes` を手で書く。
- 問題文 (`text`) は使わない (イラストが問題文)。

#### ヒントとペナルティ

| 種類 | ID | ペナルティ (仮) |
|---|---|---|
| 状況説明ヒント | `situation` | 50 秒 |
| いらすとやヒント | `irasutoya` | 40 秒 |
| 文字種ヒント | `charTypes` | 20 秒 |

- ペナルティの秒数は `src/shared/modes/palindrome/` の定数にまとめ、後から変えられるようにする (値は未確定)。
- ヒントは問題ごと・参加者ごとに開ける。開けた内容はその参加者と司会者にだけ送る。
- 開けるのは出題中で、まだ正解していないときだけ。誤操作を防ぐため、参加者の画面では加算される秒数を示して確認してから開ける。
- 旧仕様の「司会者が文字を開けるヒント」は廃止した。

#### 回答の検証

クライアント (送信前) とサーバー (受信時) で、`shared` の同じ関数を使う。

1. 前後と途中の空白を除く (それ以外の正規化はしない。カタカナの自動変換もしない)。
2. ひらがな (と長音「ー」) 以外が含まれていないか → 「ひらがなで入力してください」
3. 文字数が想定解と一致するか → 「N 文字で入力してください (現在 M 文字)」
4. 回文か (文字列を逆にして完全に一致するか) → 「回文になっていません」
5. 同じ問題ですでに送って不正解だった回答と同じでないか → 「その回答はすでに送っています」
6. ここまで通ったら、想定解と別解のどれかと完全に一致すれば正解、そうでなければ誤答。

- 1〜5 で弾いた回答はサーバーに送らず、誤答の回数にも数えない。サーバーに届いても `CommandError` で拒否し、記録しない。
- 文字数は正規化後の文字数で数える (「きゃ」は 2 文字、「ー」も 1 文字)。
- 回文の判定は完全一致とする。小書き文字 (ゃ と や)、濁点 (が と か)、長音の扱いを緩めるかは主催者に確認する。

#### 時間と順位

- 経過時間は、サーバーが出題した時刻から、正解の回答を**サーバーが受け取った時刻**までとする
  (ペナルティが数十秒単位なので、早押しのような時刻の補正はしない)。
- **記録時間** = 経過時間 + 開けたヒントのペナルティの合計。
- **問題ごとの順位**: 正解者を記録時間の短い順に並べ、同じなら誤答の少ない順。まだ正解していない人はその後ろに並べる。
- 司会者が問題を終了した時点で正解していない人は、その問題を不正解とする。
- **総合順位**: 正解した問題の数が多い順 → 正解した問題の記録時間の合計が短い順 → 全問題の誤答の合計が少ない順。
- 順位の計算は純粋関数にして、各画面と総合順位で共通に使う。得点のような値は state に持たず、記録から毎回計算する。

#### state とコマンド

- state: `phase` (`waiting` / `open` / `closed` / `finished`)、`history[]` (出題順の問題ごとの記録)、`showStandings` (モニターに総合順位を出すか)。
- 問題ごとの記録: `questionId`、`openedAt`、`closedAt`、参加者ごとの `{hints: {種類: 開けた時刻}, wrong: [{text, at}], correctAt}`。
- コマンド:
  - 司会者: `next` (現在の問題が出題中なら終了してから次へ)、`close` (問題を終了)、`finish` (企画を終える)、`showStandings {show}`
  - 参加者: `openHint {kind}`、`answer {text}`
  - AI の代理 (`system` のみ): `openHint` と `answer` に省略可能な `participantId` を付けて送る
- 投影:
  - 想定解・別解・表記・ヒントの本文は、`closed` になるまで司会者以外に送らない。参加者には自分が開けたヒントの本文だけを送る。
  - 他の参加者の回答本文は送らない。順位の表示に必要な情報 (正解したか、記録時間、誤答数、開けたヒントの種類) だけを送る。

#### 画面

- **司会者**: イラスト・答え・3 種類のヒント、参加者ごとの状況 (開けたヒント、誤答、正解時間) と順位、AI の状態。
  「問題を終了」「次の問題へ」「総合順位を表示」「企画を終える」ボタン。
- **参加者**: イラスト (タップで拡大)、文字数 (マス目)、経過時間。3 種類のヒントを開けるボタンと、開けたヒントの本文。
  回答欄はリアルタイムに検証してエラーを出し、条件を満たすまで送信できない。自分の誤答の一覧。正解後は記録時間と現在の順位。
- **モニター** (1920×1080): イラストと文字数 (全員が共通に知っている情報) と、この問題の順位 (正解者は記録時間、挑戦中の人は開けたヒントの種類)。
  問題を終了したら答え (ひらがなと表記) も出す。`showStandings` のときは総合順位を出す。
- **問題編集**: 画像のアップロード、答え (回文かをその場で確認)、表記 (文字種ヒントのプレビュー)、3 種類のヒント、別解。

#### AI 参加者

- `Participant` に `kind: 'human' | 'ai'` を加える。AI は司会者画面から追加し、トークンを持たず接続もしない。
- `apply` からは外部 API を呼ばない。サーバーの `src/server/ai/` が `GameManager.onChange` で出題を検知し、
  AI ごとに次の流れを非同期で進め、結果を `openHint` と `answer` のコマンドとして `manager.execute` に送る (イベントログに残るので、取り消しや再起動のあとも再生できる)。
  1. ルール、イラスト、文字数を与えて回答させる (ヒントなし)。
  2. 不正解なら、次のヒントを開けて (`openHint` を送ってペナルティを受ける)、「不正解だった」ことと誤答、ヒントの本文を同じ会話に足して、もう一度回答させる。
  3. 3 種類のヒントを全部開けても正解できなければ、それ以上は回答しない (終了時に不正解になる)。
- AI がヒントを開ける順番は、ペナルティの軽い順 (文字種 → いらすとや → 状況説明) を既定にし、設定で変えられるようにする。
- 検証エラー (ひらがな以外、文字数違い、回文でない) の回答はコマンドを送らず、エラー内容を添えて同じ段階で最大 2 回まで答え直させる。
  それでも通らなければ、その段階は不正解として次のヒントに進む。
- 呼び出したときの問題 ID を覚えておき、返ってきたときに問題が変わっていたり終了していたりしたら捨てる。同じ AI について同時に複数の呼び出しをしない。
- 再起動などで流れが途切れたときは、司会者が再実行すると、記録 (開けたヒントと誤答) から会話を作り直して続きから進める。
- API:
  - SDK は `@anthropic-ai/sdk`、モデルは `claude-opus-5` (画像入力に対応。料金は入力 $5 / 出力 $25 per 1M トークン)。
    日本語の文字数を数えて回文を組み立てる推論が要るので、推論の強いモデルを使う。モデル名と `effort` は環境変数で変えられるようにする。
  - `thinking: {type: 'adaptive'}`、`output_config.effort: 'high'`。`budget_tokens` は使えない (400 になる)。
  - 出力は構造化出力 (`output_config.format` の JSON スキーマ) で `{answer: string}`。
  - 会話は段階ごとに前の応答 (`content` を思考ブロックごと) をそのまま履歴に足していく。画像を含む先頭の部分はプロンプトキャッシュを効かせる。
  - `stop_reason === 'refusal'` を確認してから `content` を読む。サーバー側フォールバック (`fallbacks: 'default'`、ベータ `server-side-fallback-2026-07-01`) を有効にする。
  - タイムアウトは 1 回あたり数分 (TypeScript SDK の `timeout` はミリ秒)。AI の考える時間もそのまま経過時間に含まれる。
  - `ANTHROPIC_API_KEY` が未設定なら AI を無効にし、司会者画面にその旨を出す。
  - 費用の目安: 1 問あたり AI 1 体で最大 4 回 (答え直しを除く) 呼ぶ。20 問で最大 80 回、$5〜10 程度。
- プロンプト、モデル、`usage`、回答、かかった時間を、ログと SQLite の `ai_calls` テーブルに残す。

### 感想戦 (共通)

- `history` を順番にめくる「review モード」を共通の部品にする。司会者 (リスニング数学ではモニター) が前後に移動する。
