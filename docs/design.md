# 全体設計・拡張計画

## 目的

オフラインイベントで行う複数のクイズ企画で共通して使う、LAN 内限定の Web アプリ。
司会者・参加者・モニター・問題編集の4画面がリアルタイムに同期する。
企画 (mode) はプラグインとして追加できるようにする。

| 企画 | mode ID | 司会者 | 参加者 | モニター | 編集 | 感想戦 |
|---|---|---|---|---|---|---|
| シンプル早押しクイズ | `simple-buzzer` | ○ | ○ | ○ | ○ | ○ |
| 早押しクイズ (ボード付き) | `buzzer-board` | ○ | ○ | ○ | ○ | ○ |
| リスニング数学 | `listening-math` | – | – | ○ (再生と操作) | ○ | ○ (モニターから操作) |
| イラスト回文クイズ | `palindrome` | ○ | ○ | ○ | ○ | ○ |

## 中核の設計

### Game と Mode

- **Game** は1つの企画の実施インスタンス (`id, mode, title, questions, participants, state`)。
  リハーサル用と本番用のように、同じ mode で複数の Game を作れる。
- **ModeDefinition** (`src/shared/modes/types.ts`) は次のものを持つ:
  - `questionExtraSchema`: 企画ごとの問題の追加フィールド (genre、画像、ヒント、音声など)
  - `commandSchema`: 企画固有のコマンド (zod の discriminated union)
  - `permissions`: コマンドごとに実行できる role
  - `initialState()` / `apply(game, command, ctx)`: エンジンが渡した Game のコピーを書き換える。`ctx` にサーバー時刻と実行者が入る。
    外部の状態に依存しないので、イベントログを再生すれば同じ状態を再現できる (取り消しに使う)
  - `project(game, viewer)`: 閲覧者ごとに送る情報を絞る (参加者やモニターに未出題の答えを送らない)
- クライアント側の `src/client/modes/registry.ts` に、mode ごとの画面コンポーネントを登録する。

**新しい企画を追加する手順**: `src/shared/modes/<mode>/` に ModeDefinition を書く → shared の registry に登録 →
`src/client/modes/<mode>/` に画面を書く → client の registry に登録。サーバー側のコードは変えなくてよい。

### 同期モデル (サーバーが唯一の正)

1. クライアントは `command` を送るだけ。
2. サーバーは権限を確認し、zod で検証してから `apply` を適用する。
3. イベントを SQLite に追記し、Game のスナップショットを更新する。
4. 閲覧者の種類ごとに `project()` した Game 全体をブロードキャストする (単調増加の `version` 付き)。

- room は `game:{id}:host` / `:monitor` / `:participant:{pid}`。
- 数十人規模なので差分は送らず、毎回 state 全体を送る。
- 問題の編集も共通コマンド (`questions.*`) として同じ経路を通るので、編集画面と司会者画面が常に一致する。
- 取り消し (undo): 直近の操作 (問題の編集と参加登録を除く) を除いてイベントログを最初から再生し、状態を作り直す。
- イベントログは感想戦や監査にも使える。

### 認証 (LAN 前提の軽いもの)

- 参加者: 名前を登録するとサーバーがトークンを発行する。トークンは localStorage に保存し、再読込しても同じ参加者に戻れる。
- 司会者と問題編集: 環境変数 `HOST_PASSWORD` で保護する (未設定なら誰でも使える)。
- モニター: 閲覧のみなので認証しない。ただし答えなど秘匿すべき情報は投影で除く。
  - 例外として、モニターから操作する企画 (`ModeDefinition.monitorRequiresHost` が true) では、モニターの購読にも司会者パスワードを求める。
    そのような企画に限り、`permissions` (と `reviewPermissions`) に `'monitor'` を書いたコマンドをモニターから実行できる。
    それ以外の企画のモニターからのコマンドは、サーバーが一律に拒否する。
  - どの企画かは購読前に分からないので、クライアントの `MonitorPage` は `listGames` の結果から企画を調べて `HostGate` を通す。

### 早押しの公平性

- クライアントはサーバーと ping を交換して時計のオフセットを推定する (NTP 方式で、RTT が最小のサンプルを採用)。
- `touchstart` / `pointerdown` / `keydown` (Enter・Space) で押した瞬間の時刻をサーバー時刻に換算して送る。
- サーバーは申告された時刻を `[受信時刻 - 500ms, 受信時刻]` に丸めて使う。まだ判定していない押下だけを時刻順に並べ直す。

### モニター (16:9)

`MonitorStage` が 1920×1080 固定のステージを `transform: scale()` で画面に合わせる。スクロールは出さない。

## 企画ごとの拡張計画

### simple-buzzer (フェーズ1)

- 押した順に回答権を得る。正解 +1、誤答 -1。誤答した人はその問題でボタンを押せない。
- 押した人が全員誤答したら読み上げを再開する。参加者全員が誤答したら問題を終了する。
- 司会者の補正操作: 押下のリセット、問題のスキップ、再オープン、得点の直接編集、参加者の削除。
- 出題ごとの記録 `history` (出題前の得点、押下と判定) を残しておき、感想戦で使う。

### buzzer-board

- simple-buzzer の reducer とは別に実装する。ただし押下の受付や時刻補正などの部品は共通化する。
- 追加する state: 休みの残り問題数、勝ち抜け、連答カウンタ、ジャンル選択権、ボード回答 (提出、仮判定、確定)。
- 問題の追加フィールド: `genre` (13種)。次の問題はジャンルの中からランダムに選ぶ (乱数シードをコマンドに埋め込んで決定論的に選択する)。

#### 仕様と解釈の決定事項
- **その時点での早押し参加者の数**: 誤答した時点で勝ち抜けていない参加者の数 (誤答した本人を含み、休み中の人も含む)。誤答時の休み問題数は `min(その時点での早押し参加者の数, 5)` 問。
- **休みの消化**: 休み中の人は、以後に出題された問題の数だけ休み数が減る (スルーでボードクイズになった問題も1問と数える)。出題が取り消された (cancel) 問題は数えない。
- **連答が途切れる条件**: 直前の問題でその人が早押しで正解していなければ途切れる (他の人の正解、誤答、スルー、出題の取り消し)。
- **勝ち抜けた人の点**: 5ポイントに達したら早押しパートを勝ち抜け。早押しパートで獲得できるポイントの上限は5点であり、5点を超えたら5に戻す。5ポイントに戻したあと、ボードクイズの正解で5を超えて得点できる。
- **ジャンルの自動選択**: 1問目、誤答の次の問題、スルー (ボードクイズ) の次の問題では、「未出題の問題が最も多いジャンル」が自動で選ばれる。同数のジャンルが複数あるときはジャンル一覧の定義順 (ノンジャンル、スポーツ、世界史、公民、地理、文学、日本史、漫画・アニメ・ゲーム、生活、科学、芸能、芸術、言葉) で先頭のものが選ばれる。
- **ジャンル選択権**: 早押しで正解した人が次のジャンルを選べる。正解者が勝ち抜けた場合 (5ポイントに達した場合) もジャンルを選択できる。
- **回答権**: 最初に押した1人のみ。2番目以降の押下は記録するが回答権は与えられず、判定が出た時点でその問題は終了する。

### listening-math

問題音声をモニター (会場のテレビにつないだ PC) からノンストップで流し、解答者は紙の解答用紙に答えを書く。
システムでの回答の送信や採点はしない。司会者画面と参加者画面はなく、操作はモニター画面で直接行う (司会者パスワードが要る)。

#### 問題のデータ

| フィールド | 例 | 説明 |
|---|---|---|
| `text` (共通) | xの2乗マイナス5xプラス6イコールゼロの解の和は? | 読み上げに適した形で書く (数式は描画しない)。振り返りで表示する |
| `answer` (共通) | `5` | 振り返りで表示する |
| `extra.audio` | メディア ID | 問題音声 (#12 でアップロード)。空なら出題を開始できない (TSV で問題文だけ先に取り込めるよう、登録時は必須にしない) |
| `extra.explanation` | 解と係数の関係より $x^2 - 5x + 6 = 0$ の… | 解説。複数行で書ける。Markdown と同じく `$...$` (インライン) と `$$...$$` (ディスプレイ) で TeX 記法の数式を埋め込み、KaTeX で描画する。`\$` はただの `$`。振り返りでモニターに大きく表示する |
| `extra.source` | `オリジナル`、`2019 AMC 12A Problem 19 (改)` | 出典。振り返りでモニターに小さく表示する |

TSV の追加列は「解説」「出典」「音声 ID」の順。

#### state とコマンド

- state: `phase` (`idle` / `playing` / `played`)、`currentIndex` (再生中、または停止時に再生していた問題)、`startedAt`、`intervalSeconds` (問題の間隔。既定 0 秒)。
  振り返りは共通の `game.review` を使う (`reviewItems` は全問題を並び順に返す)。
- コマンド (権限は `monitor` と `host`): `play {index?}`、`progress {index}` (モニターが今再生している問題を報告する)、`stop`、`finish` (全問を再生し終えた)、`setInterval {seconds}`。
  振り返りの `review.*` も `reviewPermissions` でモニターから実行できる。
- 投影: 振り返り中でなければ、司会者以外には問題文・正解・解説・出典を送らず、音声 ID だけを送る (出題中にうっかり表示しないように)。

#### モニター画面

- ブラウザの自動再生制限があるので、最初に「音声を有効にする」ボタンを押してもらう。再読込したときも押し直す。
- 音声は Web Audio API (`AudioContext` を1つ使い回す) で再生する。次の音声を先に読み込んで復号し、前の音声が終わる時刻ちょうどに鳴るよう予約するので、曲間に空白が出ない。
- 再生はサーバーの state に従う。`phase` が `playing` のあいだ `currentIndex` の問題から連続再生し、問題が変わるたびに `progress` を送る。
  再読込すると、音声の有効化のあと、報告済みの問題の最初から再開する。
- 出題中は「第 N 問 / 全 M 問」と進捗バーだけを表示する。Space で一時停止・再開、← → で前後の問題へ、Esc で停止。
- 振り返りでは問題文・正解・解説 (KaTeX)・出典を表示する。Space でその問題の音声を再生・停止、← → で移動、Esc で振り返りを終える。

### palindrome

回文を表すイラストと文字数を見て、ひらがなの回文を答える。競技プログラミングのコンテストと同じ形式で行う (#18)。
司会者が開始すると全ての問題が同時に公開され、参加者は好きな問題から解き、分かった問題の答えをいつでも送る。
制限時間が過ぎるまで、何度でも回答できる。参加者はヒントを自分の判断で開けられるが、開けるとその問題を正解したときにペナルティの時間が加わる。
AI も参加者として参加する。

#### 問題のデータ

| フィールド | 例 | 説明 |
|---|---|---|
| `answer` (共通) | `まくらからくま` | 想定解。ひらがなの回文。保存時に検証する |
| `extra.image` | メディア ID | 回文を表すイラスト (#12 でアップロード) |
| `extra.notation` | `枕から熊` | 自然な表記。文字種ヒントの元になり、終了後にモニターにも出す |
| `extra.altAnswers` | `[]` | 別解 (ひらがなの回文。想定解と同じ文字数)。省略可 |
| `extra.hints.situation` | 動物がある寝具から出てきているようです。 | 状況説明ヒント |
| `extra.hints.irasutoya` | 「枕のイラスト」、「熊のキャラクター（四つ足）」が使われています。 | いらすとやヒント |
| `extra.hints.charTypes` | `漢ああ漢` | 文字種ヒント。省略すると `notation` から自動で作る |

- 文字種ヒントの自動生成: `notation` の各文字を、ひらがな → `あ`、カタカナ → `ア`、漢字 → `漢`、英字 → `A` に置き換える。
  長音「ー」は直前の文字と同じ文字種にする。自動生成がおかしいときだけ `charTypes` を手で書く。
- 問題文 (`text`) は使わない (イラストが問題文)。
- 問題には、開始時点の並び順に A, B, C… と番号を振る (27 問目以降は数字)。

#### ヒントとペナルティ

| 種類 | ID | ペナルティ (仮) |
|---|---|---|
| 状況説明ヒント | `situation` | 50 秒 |
| いらすとやヒント | `irasutoya` | 40 秒 |
| 文字種ヒント | `charTypes` | 20 秒 |

- ペナルティの秒数は `src/shared/modes/palindrome/types.ts` の定数にまとめ、後から変えられるようにする (値は未確定)。
- ヒントは問題ごと・参加者ごとに開ける。開けた内容はその参加者と司会者にだけ送る (終了後は全員に公開する)。
- 開けるのは受付中で、その問題をまだ正解していないときだけ。誤操作を防ぐため、参加者の画面では加算される秒数を示して確認してから開ける。
- ペナルティが加わるのは、正解した問題で開けたヒントだけ。正解できなかった問題で開けたヒントは順位に影響しない。

#### 回答の検証

クライアント (送信前) とサーバー (受信時) で、`shared` の同じ関数を使う。

1. 前後と途中の空白を除く (それ以外の正規化はしない。カタカナの自動変換もしない)。
2. ひらがな (と長音「ー」) 以外が含まれていないか → 「ひらがなで入力してください」
3. 文字数が想定解と一致するか → 「N 文字で入力してください (現在 M 文字)」
4. 回文か (逆にして一致するか) → 「回文になっていません」
5. 同じ問題ですでに送って不正解だった回答と同じでないか → 「その回答はすでに送っています」
6. ここまで通ったら、想定解と別解のどれかと完全に一致すれば正解、そうでなければ誤答。

- 1〜5 で弾いた回答はサーバーに送らず、誤答の回数にも数えない。サーバーに届いても `CommandError` で拒否し、記録しない。
- 文字数は正規化後の文字数で数える (「きゃ」は 2 文字、「ー」も 1 文字)。
- 回文の判定では、小書き文字 (ゃ と や、っ と つ など)、濁点 (が と か など)、半濁点 (ぱ と は など) はそれぞれ同じ文字として扱い、判定を緩める。長音「ー」に関しては省略とみなさず、そのまま1文字として扱う。想定解・別解との照合 (6) は完全一致とする。

#### コンテストの進行

- 司会者は開始前に制限時間 (既定 30 分、1〜300 分) を決め、開始ボタンを押す。開始した時点の問題の並びでコンテストを行い、あとから追加した問題は含めない。
- 終了予定時刻 = 開始時刻 + 制限時間 + 延長分。司会者は開催中に時間を延長できる。
- 回答とヒントを受け付けるのは、開始してから終了予定時刻の前まで (`isAccepting`)。サーバーにタイマーは置かず、時間切れの後に届いたコマンドは `CommandError` で拒否する。
  イベントログはサーバーが受け取った時刻で再生するので、取り消し (undo) をしても判定は変わらない。
- 司会者は `finish` でコンテストを終える。時間内なら打ち切り、時間切れの後なら結果の確定になる。`finish` の後 (または感想戦中) に、答えを全員に公開する。
- 残り時間は、各画面がサーバーとの時計のずれ (`src/client/lib/clock.ts`) を補正して表示する。

#### 順位

- **正解時間**は、コンテストの開始から、正解の回答を**サーバーが受け取った時刻**までとする
  (ペナルティが数十秒単位なので、早押しのような時刻の補正はしない)。
- 問題ごとの順位はない。**総合順位**は次の順に並べ、すべて同じなら同順位 (1, 2, 2, 4…)。
  1. 正答数の多い順
  2. 最終正答時間 (最後に正解した問題の正解時間) + 正解した問題で開けたヒントのペナルティの合計 が短い順
  3. 正解した問題の誤答の合計が少ない順
- 問題ごとに最初に正解した人 (正解時刻の最も早い人) を「最初の正解者」とし、スコアボードと感想戦で強調する。
- 順位の計算は純粋関数 (`computeStandings`、`computeQuestionSummary`) にして、各画面で共通に使う。得点のような値は state に持たず、記録から毎回計算する。

#### state とコマンド

- state: `phase` (`waiting` / `running` / `finished`)、`durationMs`、`startedAt`、`endsAt`、`finishedAt`、
  `questionIds` (開始時点の問題の並び)、`attempts` (問題 ID → 参加者 ID → `{hints: {種類: 開けた時刻}, wrong: [{text, at}], correctAt}`)。
  時間切れの後も `finish` までは `running` のまま (受け付けるかどうかは時刻で決める)。
- コマンド:
  - 司会者: `setDuration {minutes}` (開始前のみ)、`start`、`extend {minutes}`、`finish`
  - 参加者: `openHint {questionId, kind}`、`answer {questionId, text}`
  - AI の代理 (`system` のみ): `openHint` と `answer` に省略可能な `participantId` を付けて送る
- 感想戦は共通の `review.*` を使う。`reviewItems` は `questionIds` の順に全問題を返す。
- 投影:
  - 開始前は、司会者以外に問題を送らない。
  - 開催中は、想定解・別解・表記・メモを司会者以外に送らない。ヒントの本文は、開けた参加者本人にだけ送る。
  - 終了後 (`finished`) と感想戦中は、答え・表記・別解・全てのヒントを公開する。
  - 他の参加者の誤答の本文は送らない。順位の表示に必要な情報 (正解時刻、誤答数、開けたヒントの種類) だけを送る。

#### 画面

- **司会者**: 開始前は制限時間の設定と開始ボタン。開催中は残り時間、延長 (+1 分・+5 分・任意)、打ち切り。時間切れの後は結果の確定。
  スコアボード、問題ごとの答え・ヒント・正解者・参加者ごとの誤答の本文。終了後は「感想戦を始める」。感想戦中は共通の `ReviewControls`。
- **参加者**: 残り時間、自分の正答数と順位。問題のタブ (A, B, C… 正解・誤答の状態付き) と順位表のタブ。
  選んだ問題のイラスト (タップで拡大)・文字数のマス・3 種類のヒント・回答欄 (リアルタイムに検証し、条件を満たすまで送信できない)・自分の誤答の一覧。
  時間切れの後は入力を閉じ、終了後は答えと表記を表示する。
- **モニター** (1920×1080): 開始前はタイトル・問題数・制限時間。開催中と終了後は残り時間 (または「終了」) とスコアボード
  (順位、名前、正答数、時間とペナルティ、問題ごとの正解時間・誤答数・開けたヒント、最初の正解者の強調)。
  12 人を超えるときは 8 秒ごとにページを送る。
- **感想戦のモニター**: 問題番号、イラスト、答え (ひらがな・表記・別解)、3 種類のヒント、正解者数、正解者の一覧 (正解時間・開けたヒント)、最初の正解者。
- **問題編集**: 画像のアップロード、答え (回文かをその場で確認)、表記 (文字種ヒントのプレビュー)、3 種類のヒント、別解。

#### AI 参加者 (#15)

- `Participant` に `kind: 'human' | 'ai'` を加える。AI は司会者画面から追加し、トークンを持たず接続もしない。
- `apply` からは外部 API を呼ばない。サーバーの `src/server/ai/` が `GameManager.onChange` でコンテストの開始を検知し、
  AI ごとに `questionIds` の順に 1 問ずつ次の流れを非同期で進め、結果を `openHint` と `answer` のコマンドとして `manager.execute` に送る
  (イベントログに残るので、取り消しや再起動のあとも再生できる)。
  1. ルール、イラスト、文字数を与えて回答させる (ヒントなし)。
  2. 不正解なら、次のヒントを開けて (`openHint` を送る)、「不正解だった」ことと誤答、ヒントの本文を同じ会話に足して、もう一度回答させる。
  3. 3 種類のヒントを全部開けても正解できなければ、その問題を諦めて次の問題に進む。全問題を終えるか、コンテストが終わったら止まる。
- AI がヒントを開ける順番は、ペナルティの軽い順 (文字種 → いらすとや → 状況説明) を既定にし、設定で変えられるようにする。
- 検証エラー (ひらがな以外、文字数違い、回文でない) の回答はコマンドを送らず、エラー内容を添えて同じ段階で最大 2 回まで答え直させる。
  それでも通らなければ、その段階は不正解として次のヒントに進む。
- 回答が返ってきたときにコンテストが終わっていたり、取り消しで開始前に戻っていたりしたら捨てる。同じ AI について同時に複数の呼び出しをしない。
- 再起動などで流れが途切れたときは、司会者が再実行すると、記録 (`attempts`) から、まだ正解していない最初の問題の会話を作り直して続きから進める。
- API:
  - SDK は `@anthropic-ai/sdk`、モデルは `claude-opus-5` (画像入力に対応。料金は入力 $5 / 出力 $25 per 1M トークン)。
    日本語の文字数を数えて回文を組み立てる推論が要るので、推論の強いモデルを使う。モデル名と `effort` は環境変数で変えられるようにする。
  - `thinking: {type: 'adaptive'}`、`output_config.effort: 'high'`。`budget_tokens` は使えない (400 になる)。
  - 出力は構造化出力 (`output_config.format` の JSON スキーマ) で `{answer: string}`。
  - 会話は段階ごとに前の応答 (`content` を思考ブロックごと) をそのまま履歴に足していく。画像を含む先頭の部分はプロンプトキャッシュを効かせる。
  - `stop_reason === 'refusal'` を確認してから `content` を読む。サーバー側フォールバック (`fallbacks: 'default'`、ベータ `server-side-fallback-2026-07-01`) を有効にする。
  - タイムアウトは 1 回あたり数分 (TypeScript SDK の `timeout` はミリ秒)。AI の考える時間もそのまま正解時間に含まれる。
  - `ANTHROPIC_API_KEY` が未設定なら AI を無効にし、司会者画面にその旨を出す。
  - 費用の目安: 1 問あたり AI 1 体で最大 4 回 (答え直しを除く) 呼ぶ。20 問で最大 80 回、$5〜10 程度。
- プロンプト、モデル、`usage`、回答、かかった時間を、ログと SQLite の `ai_calls` テーブルに残す。
